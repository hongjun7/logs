> **1분 요약.** Rust로 빠른 알고리즘을 구현하면 컴파일러가 소유권과 수명에 관한 여러 실수를 검사해 준다. 그러나 정확성을 보장하려면 수학적 불변식, 정수 범위에 대한 검토, 테스트가 여전히 필요하다. 안정 버전 컴파일러와 작은 단일 파일 템플릿으로 시작하고, 채점 서버가 실제로 쓰는 도구 환경을 확인한다. 이 작업 흐름이 제대로 동작한 뒤에 자동화를 더한다.

**읽는 순서.** 비용 모델과 완전한 프로그램부터 읽고, 소유권과 BFS의 증명으로 이어가면 된다. 뒷부분에서는 테스트 방법과 선택적인 대회 도구의 역할을 설명한다. 반복문, 배열, 기초적인 그래프 개념을 알고 있다고 가정한다.

## 1. 언어보다 알고리즘을 먼저 고른다

입력 크기를 $$n$$이라 하자. $$O(n\log n)$$과 같은 시간 복잡도는 충분히 큰 $$n$$에서 상수 배를 제외한 증가율의 상한을 나타낸다. 특정 실행 시간을 보장하지는 않는다. 매 반복마다 메모리를 할당하는 $$O(n)$$ 프로그램은 입력이 작을 때 $$O(n\log n)$$ 프로그램보다 느릴 수 있다. 반대로, 채점 조건이 거의 선형인 처리를 요구할 때는 상수 배를 줄이는 것만으로 $$O(n^2)$$ 알고리즘을 살릴 수 없다.

$$n=200{,}000$$이면 이중 반복문은 약 $$4\times10^{10}$$번 반복한다. 정렬에는 비교 연산에 해당하는 작업이 대략 $$n\log_2 n\approx3.52\times10^6$$회 필요하다. 이는 **연산량 추정치**이며 Rust나 CPU를 측정한 결과가 아니다. 이 추정으로 가능성이 낮은 접근을 걸러 낸 뒤, 실제 문제를 대표하는 구현을 측정해야 한다.

문제의 제약 조건도 명세의 일부다. 절댓값이 각각 $$B$$ 이하인 값 $$n$$개를 더하면

$$
\left\vert \sum_{i=1}^{n}a_i\right\vert \le nB.
$$

$$n\le2\times10^5$$이고 $$B\le10^9$$이면 합은 $$2\times10^{14}$$까지 커질 수 있다. `i64`에는 들어가지만 `i32`에는 들어가지 않는다. 부호 있는 $$b$$비트 정수의 표현 범위는 $$[-2^{b-1},2^{b-1}-1]$$이다. 최종 답뿐 아니라 중간 곱셈의 범위도 증명해야 한다. 두 피연산자가 모두 `i64`라면 곱한 뒤에 형을 변환해도 이미 발생한 오버플로를 되돌릴 수 없다.

## 2. 작지만 완전한 시작 프로그램

다음 프로그램은 의도적으로 단순한 문제를 푼다. 부호 있는 정수 $$n$$개를 읽어 합을 출력한다. 입력은 공백으로 구분한 유효한 정수이며, $$n\le200{,}000$$과 $$\vert a_i\vert \le10^9$$를 만족한다고 가정한다.

```rust
use std::io::{self, Read};

fn main() {
    let mut input = String::new();
    io::stdin().read_to_string(&mut input).unwrap();
    let mut it = input.split_whitespace();
    let n: usize = it.next().unwrap().parse().unwrap();
    let mut sum: i64 = 0;
    for _ in 0..n {
        let x: i64 = it.next().unwrap().parse().unwrap();
        sum += x;
    }
    println!("{sum}");
}
```

이 템플릿은 입력 문자열이 $$L$$바이트일 때 $$O(L)$$ 메모리를 사용한다. 일반적인 고정 폭 정수 모델에서 파싱 작업량도 $$O(L)$$이다. 비대화형 문제에 적합한 방식이다. 대화형 채점에서는 입력을 순차적으로 읽고 출력을 플러시해야 한다. EOF까지 한꺼번에 읽으면 아직 끝나지 않은 입력 스트림을 기다리게 된다.

채점 서버가 지원하는 에디션으로 로컬에서 컴파일한다.

```sh
rustc --edition=2021 -O main.rs -o main
./main < input.txt
```

에디션 2021은 예시일 뿐, 모든 채점 서버가 이를 쓴다는 뜻은 아니다. 플랫폼의 컴파일러 버전과 허용된 크레이트를 확인해야 한다. 표준적인 알고리즘에는 안정 버전 도구 체인으로 충분하다. 특정 의존성이 명시적으로 요구할 때만 nightly로 바꾼다. 최적화 옵션은 정확성의 근거가 되지 않는다.

## 3. 안전성이 보장하는 것과 보장하지 않는 것

Safe Rust의 소유권과 대여 규칙은 광범위한 메모리 오용을 막는다. 잘못된 점화식, 범위를 벗어난 접근에 따른 패닉, 교착 상태, 산술 오류까지 막아 주지는 않는다. Rust 공식 문서는 디버그 빌드의 오버플로 검사와 릴리스 빌드의 기본 래핑 동작을 설명한다. 증명에서 오버플로 검출을 요구한다면 명시적인 검사 산술을 사용해야 한다. [Rust 정수형과 오버플로](https://doc.rust-lang.org/book/ch03-02-data-types.html).

`Vec<T>`는 자신이 할당한 메모리를 소유한다. 공유 대여 `&T`는 읽기를 허용하고, 가변 대여 `&mut T`는 그 수명 동안 배타적인 접근을 부여한다. 크기가 늘어날 수 있는 벡터에서는 원소의 참조보다 **인덱스**를 저장하면 알고리즘을 작성하기 쉬운 경우가 많다. 재할당으로 원소의 위치가 바뀔 수 있으므로, 참조를 유지한 채 원소를 추가할 때 소유권 충돌이 발생하는 데는 이유가 있다.

그래프 알고리즘은 먼저 `Vec<Vec<usize>>`로 구현한다. 메모리 사용량이 중요하다면 압축 희소 행(CSR) 표현으로 모든 이웃을 하나의 연속 배열에 저장하고 $$n+1$$개의 오프셋을 함께 둘 수 있다. 정점이 $$n$$개이고 방향 간선이 $$m$$개일 때 저장 공간은 $$O(n+m)$$이다. 연속 배치는 지역성을 높일 수 있지만, 실제 순회 방식에서 측정해야 한다.

## 4. BFS의 동작을 증명한다

가중치가 없는 그래프 $$G=(V,E)$$와 시작점 $$s$$에 대해 너비 우선 탐색(BFS)은 $$s$$에서 도달 가능한 각 정점까지의 최소 간선 수를 구한다. `dist[v] = None`은 아직 발견하지 않은 정점을 뜻한다. 큐에는 발견했지만 아직 이웃을 확장하지 않은 정점이 들어 있다.

```rust
use std::collections::VecDeque;

fn bfs(graph: &[Vec<usize>], source: usize) -> Vec<Option<usize>> {
    let mut dist = vec![None; graph.len()];
    let mut queue = VecDeque::new();
    dist[source] = Some(0);
    queue.push_back(source);
    while let Some(v) = queue.pop_front() {
        let next = dist[v].unwrap() + 1;
        for &u in &graph[v] {
            if dist[u].is_none() {
                dist[u] = Some(next);
                queue.push_back(u);
            }
        }
    }
    dist
}
```

**불변식.** 정점은 거리가 줄어들지 않는 순서로 FIFO 큐에서 나오며, 부여된 각 거리는 최단 경로의 길이다. 처음에 시작점의 거리는 0이다. 최단 거리가 $$d$$인 $$v$$를 꺼냈을 때, 아직 발견하지 않은 이웃에는 $$d+1$$을 부여한다. 그 이웃으로 가는 더 짧은 경로가 있다면, 그 경로에는 거리가 $$d-1$$ 이하인 직전 정점이 있어야 한다. 그 정점은 이미 확장되었을 것이므로 이웃도 이미 발견되었어야 한다. 이는 모순이다. 각 정점은 한 번 큐에 들어가고, 저장된 각 간선도 한 번 검사한다. 따라서 시간은 $$O(\vert V\vert +\vert E\vert )$$, 보조 메모리는 $$O(\vert V\vert )$$이다.

BFS는 임의의 가중치가 있는 최단 경로 문제를 풀지 못한다. 다익스트라 알고리즘에는 음수가 아닌 가중치가 필요하다. 음수 간선이 있으면 다른 알고리즘이 필요하며, 음수 사이클 때문에 최단 경로 거리를 정의할 수 없을 수도 있다. 그래프 표현이 같다는 사실만으로 알고리즘을 서로 바꿔 쓸 수는 없다.

## 5. 모듈러 산술과 경계 조건

정수 모듈러스 $$M\ge2$$에 대해 잉여류 산술은 $$\mathbb Z/M\mathbb Z$$에서 계산한다. 등식

$$
(a+b)\bmod M=((a\bmod M)+(b\bmod M))\bmod M
$$

은 수학적으로 성립한다. 그러나 기계 구현에서는 중간 덧셈 결과도 표현할 수 있어야 한다. 더 넓은 자료형이나 오버플로가 발생하지 않는 계산 방식을 사용한다. $$a$$로 나눈다는 것은 역원을 곱한다는 뜻이며, 역원은 정확히 $$\gcd(a,M)=1$$일 때 존재한다. 페르마의 공식 $$a^{M-2}\bmod M$$에는 $$M$$이 소수이고 $$a\not\equiv0\pmod M$$이라는 조건이 추가로 필요하다.

부호 있는 정수의 `%`는 나머지 연산자다. 양의 모듈러스에 대해 표준적인 음이 아닌 잉여를 구하려면 `rem_euclid`로 의도를 나타낼 수 있다. $$0$$, $$M-1$$, $$M$$, 허용되는 경우의 음수 입력, 가능한 가장 큰 중간값을 테스트한다. 그래프 문제에서는 정점 하나, 연결되지 않은 컴포넌트, 평행 간선, 자기 루프, 재귀 호출의 스택 사용 문제를 드러낼 만큼 긴 사슬도 확인한다.

## 6. 작은 정답 프로그램과 알고리즘을 비교한다

작은 무작위 입력에서 최적화한 알고리즘을 단순한 완전 탐색 풀이와 비교하면 효과적인 테스트가 된다. 최단 경로는 아주 작은 그래프에서 경로를 열거하거나 세제곱 시간의 모든 쌍 최단 경로 알고리즘과 비교한다. 부분집합 최적화는 $$n$$이 작을 때 $$2^n$$개 부분집합을 모두 열거한다. 난수 시드와 실패를 일으킨 정확한 입력을 보관해야 한다. 그래야 재현 가능한 반례와 우연히 통과한 표본을 구별할 수 있다.

테스트는 불변식의 증명을 보완한다. 특히 경계 조건, 파싱, 인덱스 처리를 확인하는 데 유용하다. 증명은 명시된 입력 범위에서 아직 보지 못한 어떤 입력도 알고리즘을 깨뜨리지 못하는 이유를 설명한다. 디버그 바이너리와 최적화한 바이너리를 모두 실행한다. 전자는 더 많은 실행 중 검사를 수행하고, 후자는 채점 서버의 실행 방식에 더 가깝다.

## 7. 선택적인 대회 도구

기존 작업 흐름에서는 [rust-competitive-helper](https://github.com/rust-competitive-helper/rust-competitive-helper), [Competitive Companion](https://github.com/jmerle/competitive-companion), 예제 작업 공간을 사용했다. 이들은 프로젝트별 편의 도구이며 언어 자체의 필수 요소가 아니다. 설치 방법, 리스너 포트, 지원 채점 플랫폼, 도구 체인 요구 사항은 각 프로젝트의 현재 README에서 확인한다. 재현 가능한 환경을 만들기 전에는 사용할 리비전을 고정한다.

안정적인 작업 흐름은 문제 설명과 예제를 확보하고, 문제 디렉터리를 만든 뒤, 단일 파일 풀이를 구현하는 순서다. 이어 예제와 작은 정답 프로그램으로 검사하고, 채점 서버의 설정으로 컴파일한 다음, 실제 소스 파일을 제출한다. 도구가 Cargo 작업 공간을 만든다면 그 의존성과 생성된 진입점도 채점 서버가 허용하는 제출 형식에서 동작하는지 확인한다. 로컬 IDE에서 실행되었다는 사실만으로 이식성이 입증되지는 않는다.
